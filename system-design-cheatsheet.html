1. Core System Design Concepts Foundations
TermWhat it meansWhen to use it
Horizontal scalingAdd more machines (scale out)Default for stateless services at scale
Vertical scalingBigger machine (scale up)Quick fix; limited ceiling; single-point-of-failure risk
Load balancerDistributes requests across servers — Round Robin, Least Connections, IP Hash, Consistent HashingAny multi-instance service; Layer 4 (TCP) vs Layer 7 (HTTP-aware)
Consistent hashingMaps keys to nodes so minimal redistribution when nodes join/leaveSharding, routing same-domain/client to the same worker, cache clusters
CAP theoremCan't have Consistency + Availability during a network PartitionFrame any distributed-storage tradeoff (CP: HBase, Zookeeper; AP: Cassandra, DynamoDB)
PACELCExtension of CAP: even without partition, tradeoff between latency and consistency existsDeeper distributed system design — models steady-state latency/consistency tradeoff
Sharding / PartitioningSplit data across nodes by a key (client_id, hash(domain), date range)Scale writes/reads horizontally; avoid hot spots with good shard key choice
ReplicationCopies of data on multiple nodes (leader-follower or multi-leader)Fault tolerance, read scaling; beware replication lag in async setups
Strong consistencyEvery read sees the latest writeFinancial transactions, account balances, inventory counts
Eventual consistencyReplicas converge over time, short-lived stale reads possibleHigh-read systems tolerant of slight staleness — caches, DNS, social feeds
Two-phase commit (2PC)Coordinator asks all nodes to prepare, then commits only if all agreeDistributed transactions needing atomicity; slow and blocking
Saga patternSequence of local transactions with compensating rollbacks on failureMicroservices needing distributed transactions without 2PC locking
Quorum reads/writesMajority of replicas must agree (R + W > N)Tunable consistency in Cassandra, DynamoDB; balance latency vs. durability
2. Caching Performance
TermMeaningNotes
Cache-aside (Lazy loading)App checks cache first; on miss reads DB and populates cacheCache only what's needed; risk of cold start and thundering herd
Write-throughWrite goes to cache and DB simultaneouslyCache always fresh; doubles write latency
Write-back (Write-behind)Write goes to cache first, flushed to DB asynchronouslyFast writes; risk of data loss on cache crash
Read-throughCache sits in front of DB; cache fetches from DB on miss transparentlySimpler app code; cache layer owns hydration
TTL (Time-to-live)Auto-expire stale cache entries after fixed durationKeep short for frequently changing data; longer for rarely-changing reference data
LRU evictionEvict Least Recently Used when cache is fullGood for temporal locality; default in Redis
LFU evictionEvict Least Frequently UsedBetter for skewed access patterns; more overhead
Cache stampede / Thundering herdMany requests miss simultaneously and hammer DBFix: probabilistic early expiry, mutex-on-miss, or request coalescing
RedisIn-memory KV store with persistence, pub/sub, Lua scripting, sorted setsCaching, rate limiting, leaderboards, session store, pub/sub
MemcachedSimpler in-memory KV cache, multi-threadedPure caching at very high throughput; no persistence or data structures
CDN edge cacheCache static/dynamic content at edge PoPs globallyStatic assets, API responses, HTML; reduces origin load and latency

TypeExamplesBest forAvoid when
Relational (SQL) ACID PostgreSQL, MySQL, Aurora Complex joins, strict schema, transactions (billing, orders) Massive unstructured data, write-heavy at extreme scale
Key-Value O(1) Redis, DynamoDB, Memcached Fast single-key lookups, caching, rate-limit counters, sessions Range queries, complex filters, joins
Wide-column Write-heavy Cassandra, HBase, Bigtable Massive write throughput, time-series, sensor data, audit logs Ad-hoc queries, joins, transactions
Document Flexible MongoDB, Firestore, CouchDB Semi-structured JSON data, catalogs, user profiles Cross-document joins, strict relational integrity
Search / Inverted Index Full-text Elasticsearch, OpenSearch, Solr Full-text search, fuzzy/relevance ranking, log analytics Primary transactional store (eventual consistency, no ACID)
Object storage Blob S3, GCS, Azure Blob Large unstructured blobs — raw HTML, images, model checkpoints Low-latency random reads, mutable byte ranges
Graph Traversal Neo4j, Neptune, TigerGraph Relationship traversal — social graphs, fraud rings, knowledge graphs Simple tabular data without deep relationship queries
Time-series Metrics InfluxDB, TimescaleDB, Prometheus Timestamped metrics, IoT, monitoring; range aggregations Complex joins, arbitrary query patterns
Columnar (OLAP) Analytics BigQuery, Snowflake, Redshift, ClickHouse, DuckDB Analytical aggregations over large datasets (GROUP BY, window functions) Transactional workloads, frequent point updates
NewSQL Distributed SQL CockroachDB, Spanner, YugabyteDB, TiDB ACID transactions + horizontal scale; globally distributed When strong consistency latency is unacceptable
Vector Embeddings Pinecone, Weaviate, Qdrant, pgvector, Milvus ANN (approximate nearest neighbor) search over dense embeddings Exact keyword search, transactional use cases

ACID (SQL / NewSQL)

  • Atomicity — all-or-nothing
  • Consistency — valid state after each tx
  • Isolation — concurrent txs don't interfere
  • Durability — committed data survives crash
  • Use for: financial txs, inventory, billing

BASE (NoSQL / Distributed)

  • Basically Available
  • Soft state — may change over time
  • Eventually consistent
  • Scales horizontally with weaker guarantees
  • Use for: social feeds, counters, caches
4. Messaging & Queues Async
TechnologyModelBest forKey traits
Apache Kafka Log-based pub/sub with consumer groups High-throughput event streaming, CDC, audit logs, ML pipelines Durable, replayable, ordered per partition; retention configurable
Amazon SQS Managed point-to-point queue (standard + FIFO) Decoupling microservices, job queues, batch processing Standard = at-least-once; FIFO = exactly-once, ordered
Amazon SNS Fan-out pub/sub (push to multiple SQS / HTTP / Lambda) Broadcast notifications, multi-subscriber event dispatch No replay; combine with SQS for durable fan-out
RabbitMQ AMQP broker with routing (exchanges, bindings) Complex routing logic, RPC-style patterns, task queues Flexible routing; messages deleted after ack (not log-based)
Apache Pulsar Multi-layer pub/sub separating compute (broker) and storage (BookKeeper) Geo-replication, multi-tenancy, long retention Segment-based storage; better multi-region than Kafka
Redis Streams Append-only log with consumer groups Lightweight Kafka alternative, real-time event processing In-memory (optional persistence); simpler ops than Kafka
Google Pub/Sub Managed serverless pub/sub GCP-native event ingestion, IoT, analytics pipelines At-least-once delivery; 7-day message retention

Queue (Point-to-Point)

  • One producer → one consumer per message
  • Message deleted after processing
  • Good for task distribution, load leveling
  • Examples: SQS, RabbitMQ queues

Pub/Sub (Fan-Out)

  • One event → many independent consumers
  • Consumers maintain their own offset/position
  • Good for notifications, audit, analytics fan-out
  • Examples: Kafka, SNS, Pub/Sub

6. Consistency & Concurrency Models Correctness
TermMeaningExample
LinearizabilityStrongest: operations appear instantaneous; total order consistent with real timeZookeeper, etcd, Spanner
Sequential consistencyAll nodes see operations in the same order, but not necessarily real-timeTheoretical model; approximated by leader replication
Causal consistencyOperations that are causally related appear in order; concurrent ops may differMongoDB causal sessions, some CRDT systems
Eventual consistencyReplicas converge given no new writesDynamoDB, Cassandra default, S3 (now strong)
Read-your-writesClient always reads its own writes, even across replicasSession-level guarantee; route user to same replica or use sync read
Monotonic readsOnce client reads a value, future reads won't go back in timeImportant for UI consistency (e.g., showing older data after refresh)
Optimistic concurrency (OCC)Read without lock, write with version check; retry on conflictDynamoDB conditional writes, Postgres MVCC, ETags
Pessimistic lockingLock resource before reading; release after writeSQL SELECT FOR UPDATE; high contention = deadlock risk
MVCCReaders see consistent snapshot; writers don't block readersPostgreSQL, MySQL InnoDB, Oracle
CRDTData structures that merge conflicting updates automatically (e.g., counters, sets)Collaborative editors (Figma), distributed counters, shopping carts

11. Resilience Patterns Reliability
TermMeaningImplementation
Circuit breakerStop sending to a failing dependency for a cooldown; fail fastResilience4j, Hystrix, Envoy; three states: closed → open → half-open
Retry with backoffRetry failed requests with exponential delay + jitterJitter prevents synchronized retry storms; cap max retries
TimeoutAbandon request if no response in N msConnection timeout (establish) vs read timeout (data) vs write timeout
BulkheadIsolate resource pools per dependency so one failure doesn't cascadeSeparate thread pools per downstream service; container resource limits
Graceful degradationReturn partial/cached/default results when dependency failsServe stale cache, hide feature, show fallback content
Thundering herdMass simultaneous retries after recovery overwhelm the systemFix: exponential backoff + jitter, request coalescing, cache warming
Idempotency keyUnique key ensuring retried requests don't duplicate side effectsStore key + result in DB; return cached result on duplicate
Dead letter queue (DLQ)Messages that fail repeatedly are moved to a separate queue for inspectionSQS DLQ, Kafka dead-letter topic; prevents poison pill messages blocking processing
Health checksLiveness (is process alive?) and Readiness (is it ready to serve traffic?)Kubernetes liveness/readiness probes; load balancer health endpoints
Blast radiusScope of impact when a component failsDesign to contain: partial rollouts, feature flags, cell-based architecture
Chaos engineeringIntentionally inject failures to test resilienceChaos Monkey, Gremlin, AWS Fault Injection Simulator

16. ML System Design — Fundamentals ML
TermMeaning
Problem framingTranslate business need → classification / regression / ranking / retrieval / generation task
Label definitionWhat counts as positive? Explicit (click) vs implicit (dwell time). Noisy labels need smoothing/cleaning
Training/Serving skewFeatures available offline differ from what's available at inference time; most common source of production failures
Data leakageFuture information leaks into training features; leads to over-optimistic offline metrics and poor live metrics
Class imbalanceImbalanced classes (fraud, spam) require over/under-sampling, class weights, or threshold tuning
Batch inferencePrecompute predictions offline, serve from lookup — for non-urgent freshness (overnight scores, recommendations)
Online inferenceReal-time prediction per request — low latency required; model must be fast and lightweight
Model driftReal-world distribution shifts, degrading accuracy — concept drift (relationship changes) vs data drift (input distribution changes)
A/B testing / Shadow trafficA/B = split live traffic between models; shadow = log new model's predictions without serving them
Accuracy vs latency vs costML equivalent of CAP theorem — always a three-way tradeoff; quantize/distill to shift the curve

23. ML Evaluation Metrics
MetricFormula / MeaningUse when
Precision / RecallPrecision = TP/(TP+FP); Recall = TP/(TP+FN)Classification with class imbalance; choose based on cost of false positives vs negatives
